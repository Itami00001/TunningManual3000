Подход «гибкая БД + форма для заполнения» — единственно правильный для проекта с растущим объёмом данных. Программировать каждую связь — это тупик.

Ниже — **полное описание схемы БД** без единой строчки кода. Вы сможете по нему написать миграцию на чистом SQL для PostgreSQL.

---

##  Основные сущности (таблицы)

### 1. `cars` — автомобили
Хранит модели, которые пользователь выбирает в начале.
- `id` (первичный ключ)
- `brand` (текст, например "Nissan")
- `model` (текст, "Silvia S14")
- `year_start`, `year_end` (интервал выпуска, опционально)
- `engine_code` (текст, например "SR20DET" – полезно для привязки деталей)
- `default_power_hp` (стоковая мощность, целое число)

### 2. `nodes` — узлы/агрегаты
Иерархическая структура «где находится деталь». Например: «Двигатель → Головка блока → Распредвалы».
- `id`
- `name` (текст, "Двигатель")
- `parent_node_id` (ссылка на `nodes.id`, может быть NULL для корневых узлов)
- `is_critical_for_power` (булево) – влияет ли этот узел на мощность (для лепестковой диаграммы)
- `is_critical_for_handling` (булево) – влияет на управляемость
- `display_order` (целое) – для сортировки в форме

### 3. `parts` — детали
Конкретные запчасти / тюнинг-компоненты.
- `id`
- `name` (текст, "Распредвал HKS 264°")
- `node_id` (ссылка на `nodes.id`) – к какому узлу относится
- `price` (число)
- `complexity` (целое 1-5) – сложность установки
- `power_gain` (целое) – прирост мощности в л.с. (может быть отрицательным, если деталь ухудшает параметры)
- `handling_gain` (целое, например -3..+5) – влияние на управляемость
- `reliability_impact` (целое от -3 до +3) – надёжность
- `description` (текст)
- `instructions_url` (текст, ссылка на инструкцию)

### 4. `car_parts` — стоковые детали для каждого авто
Что уже установлено на машине с завода. Нужно для расчёта «что меняем».
- `id`
- `car_id` (ссылка на `cars.id`)
- `part_id` (ссылка на `parts.id`) – деталь, которая стоит сток
- `is_default` (булево, всегда TRUE для стока, но можно в будущем добавить «пользователь уже заменил»)

### 5. `part_compatibility` — прямая совместимость деталей между собой
Главная таблица гибких связей. Позволяет сказать: деталь А **подходит/не подходит** к детали Б.
- `id`
- `part_id` (ссылка на `parts.id`)
- `related_part_id` (ссылка на `parts.id`)
- `compatibility_type` (текст, значения: `'compatible'`, `'incompatible'`, `'requires'`, `'excludes'`)
  - `compatible` – можно ставить вместе (рекомендация)
  - `incompatible` – нельзя ставить вместе
  - `requires` – если есть `part_id`, то обязательно нужен `related_part_id` (например, турбина требует усиленный топливный насос)
  - `excludes` – наличие `part_id` исключает `related_part_id` (альтернатива)
- `reason` (текст) – пояснение для пользователя

### 6. `part_car_compatibility` — совместимость детали с конкретным автомобилем (или с двигателем)
Некоторые детали подходят только к определённым машинам.
- `id`
- `part_id`
- `car_id` (может быть NULL, если привязка к двигателю)
- `engine_code` (текст, NULL, если привязка к авто)
- `is_compatible` (булево) – если FALSE, то деталь вообще нельзя установить на этот авто

##  Принцип работы гибких связей

Когда пользователь собирает конфигурацию (выбирает детали из каталога), ваша логика должна:

1. Взять все выбранные `part_id`.
2. Для каждой пары `(part_id, selected_part_id)` проверить таблицу `part_compatibility`:
   - Если есть запись с `compatibility_type = 'incompatible'` → показать ошибку.
   - Если есть `requires` → проверить, что требуемая деталь тоже выбрана. Если нет — добавить её в корзину автоматически (или предупредить).
3. Для `compatible` — просто рекомендация, не блокирует.
4. Также проверить `part_car_compatibility` — если есть запись с `is_compatible = false` для данного авто, то деталь недоступна для выбора.

##  Административная форма (как наполнять БД без кода)

Подойдёт admin.html, который пишет прямо в эти таблицы. Вот что должно быть на форме:

### Форма 1: Управление узлами (`nodes`)
- Древовидный список существующих узлов.
- Кнопка «Добавить узел»: поля `name`, `parent_node` (выпадающий список), чекбоксы `is_critical_for_power`, `is_critical_for_handling`.
- Возможность редактировать/удалять.

### Форма 2: Управление деталями (`parts`)
- Выбор узла (`node_id` выпадающий список)
- Название, цена, сложность, прирост мощности и т.д.
- Поле `instructions_url` – ссылка на инструкцию (вы можете заполнять позже).

### Форма 3: Управление совместимостью деталей (`part_compatibility`) — **самая важная**
Выглядит как конструктор:
- Выпадающий список «Деталь А» (все `parts`)
- Выпадающий список «Деталь Б»
- Выбор типа связи: «Подходит», «Не подходит», «Требует», «Исключает»
- Поле «Причина» (текст)
- Кнопка «Добавить связь»

Также нужен список всех существующих связей с кнопками «Удалить».

### Форма 4: Привязка деталей к автомобилям (`part_car_compatibility`)
- Выбор детали
- Выбор авто (`cars`)
- Чекбокс «Совместима» (по умолчанию TRUE, но можно выставить FALSE для запрета)

### Форма 5: Стоковые детали для авто (`car_parts`)
- Выбор авто
- Выбор детали (только те, которые из `parts` и считаются «стоковыми» – вы можете заранее пометить их отдельным полем `is_oem` в таблице `parts`)

##  Пример заполнения, чтобы вы поняли логику

Допустим, вы добавляете турбину Garrett GT2871R.

1. Создаёте узел «Турбокомпрессор» (родитель «Двигатель»).
2. Создаёте деталь «Garrett GT2871R», привязываете к этому узлу, ставите `power_gain = +80`.
3. Создаёте деталь «Усиленный топливный насос Walbro 255».
4. В форме совместимости: Деталь А = Garrett, Деталь Б = Walbro, тип = `requires`, причина = «Турбине нужно больше топлива».
5. Для автомобиля Nissan Silvia S14 добавляете запись `part_car_compatibility` с `is_compatible = true` (если подходит).
6. Если какая-то деталь не подходит к Silvia, добавляете `is_compatible = false`.
